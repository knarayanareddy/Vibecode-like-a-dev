## 1. The ten laws

1. **The spec is the interface.** Behaviour changes start as a change to a requirement or an ADR, not as a code edit that the spec later explains.
2. **A failing test comes before behaviour.** The test names the criterion it proves with an `@req` anchor. Untested behaviour is not done, it is proposed.
3. **One term, one meaning.** If two words exist for one concept, one of them is a bug.
4. **Boundaries before bodies.** Interfaces, error shapes and data contracts are fixed while changing them is still free.
5. **The domain stays pure.** Rules live in code that imports no framework, no database and no vendor SDK.
6. **Boring technology, justified additions.** Every dependency earns an ADR naming what it replaces and what breaks without it.
7. **Fail closed.** Deny by default for authorization; refuse rather than guess; never silently degrade a security control.
8. **Make it observable.** If a failure cannot be seen in a log with a correlation ID, it will be discovered by a user.
9. **Reversible beats predictable.** Ship behind a flag or with a rollback, because the forecast is wrong more often than the rollback is used.
10. **Stop and ask before guessing.** Three failed attempts at the same failure means the model of the problem is wrong. Escalate with what you tried.

## 2. Definition of done

A requirement is done when all of the following are true. Not "mostly true".

- [ ] Every acceptance criterion for the requirement maps to a named test, or to a manual script that has been run once.
- [ ] The `@req` anchor exists in the test file and `node specs/spec-check.mjs` passes.
- [ ] Failure paths are implemented and tested, not just described.
- [ ] No new dependency without an ADR entry, and no new environment variable without documentation.
- [ ] The traceability row for the requirement is updated with the anchor path.
- [ ] The change can be reverted with one command or one flag.

## 3. Change protocol

| Change | What must happen first |
| --- | --- |
| New behaviour | Add or amend a requirement in `spec.json`, then write the failing test. |
| Changed interface or error shape | Update the contract inventory in 04-contracts.md, then the test. |
| New dependency or service | ADR in 03-architecture.md: what it replaces, what breaks without it, cost of removal. |
| Scope expansion | Edit the brief, and remove something of comparable size in the same change. |
| Test deletion or weakening | Not allowed as a fix. Mark the test skipped with a requirement reference and escalate. |
| Schema change | Forward-only migration plus the rollback or restore note in 04-contracts.md. |
