# Agent handoff

> Generated by vibecode-like-a-dev v0.3.0 · kind web-app · stage mvp · tier 1 (standard)

> This document exists because the difference between a junior and a senior engineer is not typing speed. It is what they refuse to do: invent scope, guess at requirements, weaken tests, and hide uncertainty.

## 1. How to use this packet

| You are | Start here |
| --- | --- |
| A coding agent with repo access | `AGENTS.md` in this folder, then `spec.json`, then the requirement you were given. |
| A chat-only builder | Section 2 below, then one requirement per message. |
| A human about to review | `05-verification.md` section 8, then the diff. |

## 2. Copy-paste brief

This is the message that starts a build. It is short on purpose: the packet carries the detail, and a brief nobody reads is a longer prompt.

```text
Build "Retro Board": A retrospective board for small engineering teams. A facilitator creates a board per sprint, teammates add anonymous cards into Start / Stop / Continue columns, then everyone votes and the team leaves with three agreed actions. Today teams do this in a shared doc that nobody can vote on and that loses its history.

Non-negotiable rules for this build:
1. Read specs/AGENTS.md first, then specs/07-agent-handoff.md. Follow the loop there.
2. Implement only what specs/spec.json lists as requirements. No extra endpoints, screens or abstractions.
3. Write a failing test before the behaviour, and add an @req anchor to every automated requirement.
4. Do not add a dependency without an ADR entry in specs/03-architecture.md.
5. Do not delete or weaken a test to make something pass. Stop and report instead.
6. Keep files under ~300 lines and keep the domain layer free of framework imports.

V1 scope: The primary journey works end to end; Durable state with forward-only migrations; Authentication with explicit session lifecycle; Server-side authorization with deny-by-default; Accessible primary journey; Every screen has loading, empty, error and success states; One design token source; Errors are classified before they are rendered; Versioned machine-readable interface contract; One error envelope and one identifier scheme; Abuse limits on public entry points; The product's own rules are named and pinned.
Out of scope: anything not listed above, plus the non-goals in specs/01-product-brief.md.
Stack: typescript — npm run lint && npm run typecheck && npm test.
Rigor tier: 1 (standard) — gates in specs/05-verification.md are the definition of done.

Start with Phase 0, then Phase 1. Stop after each phase and report: what changed, which tests pass, which requirement moved, what you are unsure about.
```

## 3. The loop

1. Read `spec.json` and the requirement you are about to implement. Do not read the whole packet to start; read the requirement and its document.
2. Restate the requirement in five bullets: the behaviour, the failure path, what is out of scope, the test you will write, the files you expect to touch.
3. Write the failing test first, with an `@req` anchor, matching the acceptance criteria identifier.
4. Implement the smallest change that makes the test pass. No extra abstractions, no speculative interfaces.
5. Run the check: tests, typecheck, lint, and `node specs/spec-check.mjs`.
6. Refactor only with the tests green. Then update the traceability row for that requirement.
7. Report: what changed, which requirement moved, what passed, what you are unsure about. Then stop and wait.

## 4. Hard rules

1. Implement only listed requirements, one at a time. If something is missing, ask: do not invent scope.
2. Never delete, skip or weaken a test to make a check pass. Stop and report instead.
3. Every automated requirement gets an `@req REQ-xxx` anchor in the test that proves it.
4. No new dependency without an ADR naming what it replaces; no secret in the repository.
5. Keep domain code free of framework, database and vendor imports, and files under ~300 lines.
6. Do not reformat unrelated files. Report uncertainty explicitly: a confident wrong answer costs more than a question.

## 5. Stop and escalate when

- The requirement contradicts the architecture or the domain model.
- Two requirements imply different shapes for the same interface.
- A check fails for a reason that is not in the code you wrote.
- You need a dependency, a credential or a decision that is not in the packet.
- You have attempted the same fix three times.

## 6. Tool-specific notes

| Tool | How to use this packet |
| --- | --- |
| Claude Code, Codex CLI, Cursor, Gemini CLI | Add the packet to the repo at `specs/` and point the agent at `specs/AGENTS.md`. Give one requirement per session. Ask it to run the spec check before reporting. |
| Lovable, Replit, Bolt, v0 | Paste the brief from section 2 first, then one requirement with its criteria per turn. Ask for a file list before it writes code. These tools do migrations and authorization unreliably: keep those for a human or a code agent. |
| Chat-only (ChatGPT, Claude web, etc.) | Paste the brief and the requirement. Ask for the test, then the implementation, then a review against the checklist. Short conversations, one requirement each. |
| Another agent, unknown behaviour | Start with one requirement of the smallest scope. Judge the agent on whether it wrote the failing test before the code and whether it lied about running it. |

## 7. Independent review prompt

Self-review shares the author's blind spots. Run this in a separate session, with no memory of writing the code.

```text
You are reviewing a change against a written specification. You did not write this code and you gain nothing by approving it.

Inputs: the requirement block (with acceptance criteria) and the diff.

Report in this order:
1. Requirements not implemented, or implemented beyond scope.
2. Acceptance criteria with no corresponding assertion.
3. Failure paths that are described but not handled.
4. Tests that would pass if the behaviour were wrong (weak or tautological assertions).
5. Boundary violations: framework imports in domain code, cross-context reads, missing authorization.
6. Anything a second implementer would have built differently, and whether that difference matters.

For each finding: file, line, the spec line it violates, and the smallest fix. If there are no findings in a category, say "none" rather than inventing one. Do not comment on style that the linter already covers.
```

## 8. Progress report format

Ask for this at the end of every session. A report that cannot name a requirement is a report that did nothing.

```markdown
## Progress report

- Requirement: REQ-xxx — status (done / partial / blocked)
- Tests: added, passing, and the anchor path
- Checks: lint, typecheck, tests, spec check — pass or fail
- Files changed: list, one line each
- Decisions: any ADR added or amended
- Uncertainties: what you would ask a reviewer
- Next: the next requirement you propose, and why that one
```

## 9. What good looks like

- The agent wrote the failing test first and can show it failing for the right reason.
- Every claim in the final message can be checked by running one command.
- Uncertainty appears in the report, and the next agent can continue without the chat history.
