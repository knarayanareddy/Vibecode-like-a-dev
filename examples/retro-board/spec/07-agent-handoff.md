# Agent handoff

> Generated by vibecode-like-a-dev v0.3.0 · kind web-app · stage mvp · tier 1 (standard)

This is the working brief for **Retro Board**. 14 requirements, 10 of them proven by an anchored test, 8 gates, 4 weeks, 2 people.

## 1. The message that starts a build

```text
Build "Retro Board": A retrospective board for small engineering teams. A facilitator creates a board per sprint, teammates add anonymous cards into Start / Stop / Continue columns, then everyone votes and the team leaves with three agreed actions. Today teams do this in a shared doc that nobody can vote on and that loses its history.

Non-negotiable rules for this build:
1. Read specs/AGENTS.md first, then specs/07-agent-handoff.md. Follow the loop there.
2. Implement only what specs/spec.json lists as requirements. No extra endpoints, screens or abstractions.
3. Write a failing test before the behaviour, and add an @req anchor to every automated requirement.
4. Do not add a dependency without an ADR entry in specs/03-architecture.md.
5. Do not delete or weaken a test to make something pass. Stop and report instead.
6. Keep files under ~300 lines and keep the domain layer free of framework imports.

V1 scope: The primary journey works end to end; Durable state with forward-only migrations; Authentication with explicit session lifecycle; Server-side authorization with deny-by-default; Accessible primary journey; Every screen has loading, empty, error and success states; One design token source; Errors are classified before they are rendered; Versioned machine-readable interface contract; One error envelope and one identifier scheme; Abuse limits on public entry points; The product's own rules are named and pinned.
Out of scope: anything not listed above, plus the non-goals in specs/01-product-brief.md.
Stack: typescript — npm run lint && npm run typecheck && npm test.
Rigor tier: 1 (standard) — gates in specs/05-verification.md are the definition of done.

Start with Phase 0, then Phase 1. Stop after each phase and report: what changed, which tests pass, which requirement moved, what you are unsure about.
```

## 4. Escalate instead of guessing

- A read or write of personal data would bypass the audit or retention rule.
- The requirement contradicts the architecture or the domain model.
- A check fails for a reason that is not in the code you wrote.
- You need a decision the packet does not make.
- You have attempted the same fix three times.

## 5. Independent review prompt

Run this in a separate session with no memory of writing the code. Self-review shares the author's blind spots.

```text
You are reviewing a change against a written specification. You did not write this code and you gain nothing by approving it.

Inputs: the requirement block (with acceptance criteria) and the diff.

Report in this order:
1. Requirements not implemented, or implemented beyond scope.
2. Acceptance criteria with no corresponding assertion.
3. Failure paths that are described but not handled.
4. Tests that would pass if the behaviour were wrong.
5. Boundary violations: framework imports in domain code, cross-context reads, missing authorization.

For each finding: file, line, the spec line it violates, and the smallest fix. Say "none" rather than inventing a finding.
```
