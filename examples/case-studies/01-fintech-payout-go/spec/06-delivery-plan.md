# Delivery plan

> Generated by vibecode-like-a-dev v0.21.0 · kind api · stage production · tier 3 (critical)

## 1. The shape of the work

Build the smallest end-to-end slice of **The primary journey works end to end** first: one screen or command, one operation, one storage path, one test per criterion, deployed. Then widen.

- A phase gate is a real gate. Do not start the next phase with a red check.
- Every task maps to a requirement id or a gate id. A task that maps to neither is a hobby.
- Calendar budget is 12 weeks; if the plan does not fit, cut scope in the brief — never cut gates.

## 2. Phases

### Phase 0 — Skeleton and guardrails · week 1-2

_A running, tested, documented box that can create and delete a settlement and nothing else._

- [ ] Initialise the repository with Go 1.23 and PostgreSQL; commit the lockfile.
- [ ] Add the CI workflow with lint, typecheck and test jobs, and make it required on the default branch.
- [ ] Add configuration validation that names every missing variable before the first settlement is created.
- [ ] Write the runbook: install, run, test, deploy, and what merchants see when the settlement service is down.
- [ ] Copy the specification packet into the repository and wire the spec check into CI.
- [ ] Answer the open questions that block the settlement slice; the rest can wait for their phase.

**Exit:** The documented command creates and deletes a settlement through PostgreSQL, and CI is green on that alone.

### Phase 1 — Domain core · week 3-4

_The rules that make a settlement valid, in code, before any framework is chosen for them._

- [ ] Fill the language table around a settlement: one term, one meaning, no synonyms.
- [ ] Write failing tests for each rule a settlement must satisfy, including the ones the idea states in its own words.
- [ ] Implement the settlement aggregates as pure code with no framework, network or database imports.
- [ ] Define typed errors for the ways a settlement can be rejected; no exception control flow across module boundaries.
- [ ] Run the mutation check on the settlement domain and record the baseline score.

**Exit:** A settlement rules pass their tests with no infrastructure imported — no PostgreSQL, no framework.

### Phase 2 — Contracts before implementation · week 5-6

_Every boundary around a settlement fixed while changing it is still free._

- [ ] Fix each shape in the contract inventory: REQ-009, REQ-010, REQ-019.
- [ ] Write the acceptance tests for a settlement first; they must fail for missing behaviour, not missing setup.
- [ ] Record a real response for every external dependency, or write down the stub and why.
- [ ] Record an ADR for each library that a reviewer could plausibly want removed.

**Exit:** The settlement acceptance tests exist and fail because the behaviour is missing, not because the setup is.

### Phase 3 — Vertical slices · week 7-10

_Working settlement behaviour end to end, one requirement at a time._

- [ ] REQ-004 What Fintech Payout Go knows about a settlement survives a restart in PostgreSQL, and every schema change is a forward-only migration with a restore step that has been run once. Test first, then implement, then trace.
- [ ] REQ-005 A merchant's settlement data has a stated retention period, an export, and a deletion path that removes every copy including the ones in logs and fixtures. Test first, then implement, then trace.
- [ ] REQ-018 Scope stays small because the card number is never available to the merchant's own servers. Test first, then implement, then trace.
- [ ] REQ-022 Reported numbers do not shift retroactively: corrections are forward-only adjusting entries and batch totals reconcile source-to-ledger. Test first, then implement, then trace.
- [ ] REQ-C01 When a payout exceeds 1000000 euro cents, the ledger shall require a distinct second treasury approver before posting. Test first, then implement, then trace.
- [ ] REQ-C02 When a settlement request reuses an idempotency key with altered parameters, the ledger shall reject the transfer with IDEMPOTENCY_CONFLICT. Test first, then implement, then trace.
- [ ] REQ-006 A merchant signs in and signs out, and a revoked session stops working on the server immediately rather than at the next token expiry. Test first, then implement, then trace.
- [ ] REQ-007 Reading or changing another merchant's settlement is refused by the server; the interface is allowed to hide the control but never to be the control. Test first, then implement, then trace.
- [ ] REQ-008 Two tenants cannot see or affect each other's settlement data through any query, handler or export path, and a merchant who belongs to one tenant cannot reach another's rows. Test first, then implement, then trace.
- [ ] REQ-014 Public entry points that create or change settlement data are limited per identity and per address, and say how long to wait when they refuse. Test first, then implement, then trace.
- [ ] REQ-015 Privileged changes to a settlement are append-only and attributable to an operator who made them, including the ones made by a support tool, and never to the merchant whose data changed. Test first, then implement, then trace.
- [ ] REQ-020 No single identity can move unreviewed code into the environment that touches money. Test first, then implement, then trace.
- [ ] REQ-021 The principal who initiates a material financial change or rule change can never be the sole principal who approves it into effect. Test first, then implement, then trace.
- [ ] REQ-009 The settlement interface has a versioned, machine-readable contract kept in the repository, and a breaking change fails before merge rather than after a consumer notices. Test first, then implement, then trace.
- [ ] REQ-010 Every failure on the settlement interface returns one envelope shape, with an opaque identifier a support conversation can quote. Test first, then implement, then trace.
- [ ] REQ-019 A leaked token cannot be moved to another customer or tenant without the provider rejecting it. Test first, then implement, then trace.
- [ ] REQ-011 A retried settlement request produces the same outcome as the first one: no second record, no second side effect, no second notification. Test first, then implement, then trace.
- [ ] REQ-012 Money attached to a settlement stays correct through retries, partial failure and reversal, because every correction is a new entry rather than an edit. Test first, then implement, then trace.
- [ ] REQ-013 A failed settlement operation is visible in a log with a correlation id the support team can search, without attaching a debugger to production. Test first, then implement, then trace.
- [ ] REQ-023 External auditors can trace any figure back to its originating event, approver and effective access policy across a seven-year window. Test first, then implement, then trace.
- [ ] REQ-024 Incident triage uses deterministic thresholds rather than ad-hoc judgement so statutory notification clocks start automatically on detection. Test first, then implement, then trace.
- [ ] REQ-025 Recovery time and recovery point objectives are backed by deterministic failure handling and verified restore artifacts. Test first, then implement, then trace.

**Exit:** Each of the 28 requirements is traceable from criterion to test, with its anchor green in CI.

### Phase 4 — Interface and hardening · week 11-12

_Fintech Payout Go feels finished to a merchant and fails predictably._

- [ ] Walk the threat model; each accepted mitigation becomes a control or a test.
- [ ] Add correlation IDs and one alert on error rate.
- [ ] Exercise every failure path in the requirements, manually or by test.
- [ ] Raise the mutation score to target on the domain layer.

**Exit:** All 25 gates pass in CI, and the manual checks have been run once and dated.

### Phase 5 — Release and first observation · week 13-12

_Ship a settlement change with a way back._

- [ ] Write the release checklist and the rollback procedure for a PostgreSQL migration.
- [ ] Deploy to staging and take one settlement through the primary journey there.
- [ ] Observe for one window: error rate, latency, and one settlement created by a real merchant.
- [ ] Record what changed in the spec as a result, then archive the changed requirements.

**Exit:** A release has been observed with real merchants data, and the rollback has been rehearsed or explicitly accepted as untested.

## 3. Commit and branch protocol

- One commit, one intention, prefixed with the requirement: `feat(REQ-001): runnable from a clean clone`.
- A commit that only adds tests is welcome; a commit that only weakens tests is rejected.
- Run golangci-lint run && go vet ./... && go test ./... before pushing — Go 1.23 will not tell you in CI either.
- One branch per vertical slice, and never two people inside the same settlement requirement.

## 4. Stop rules

Rules for humans and agents alike. The point is to stop the loop where the model of the problem is wrong, instead of paying for the same mistake repeatedly.

1. Three failed attempts at the same failing check: stop, write down what was tried, escalate with the evidence.
2. A test needs weakening to proceed: stop — that is either a wrong test or a wrong design.
3. A requirement about the settlement turns out to be ambiguous: stop that requirement, record the question, keep going elsewhere.
4. The phase gate cannot pass within twice its allotted time: cut scope; do not extend the phase silently.

## 5. Risk register

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| Scope creep past the 28 listed requirements | high | The non-goals table is the answer: anything unlisted is rejected in review rather than debated. |
| An invented abstraction around the settlement | medium | One context per owned noun; a new layer needs a reason a reviewer can check. |
| Environment and configuration drift | medium | Configuration is validated at startup and fails by naming the missing variable. |
| The 12-week calendar slipping | medium | Cut scope in the brief, never a gate. |
| A money path that double-counts or loses an entry | high | Ledger entries are immutable and written in the same transaction as the state change. |
| A personal-data field escaping its retention rule | high | Field-level inventory plus a deletion test that asserts zero rows remain. |

v1 is finished when all 25 gates in `05-verification.md` pass, every manual check is dated, and `spec.json` describes what was actually built — including the decisions that changed on the way.
