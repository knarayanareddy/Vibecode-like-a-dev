## 1. The laws, and what they mean here

The left column is law for every project this factory compiles. The right column is what that law obliges here — when the two seem to conflict, the right column is wrong and belongs back in the compiler.

| Law | In Fintech Payout Go |
| --- | --- |
| The spec is the interface. | A change to how a settlement behaves starts as a change to a requirement or an ADR — never as a code edit the spec is later bent to match. |
| A failing test comes before behaviour. | 26 of 28 requirements are proven by a test carrying `@req`; the rest carry a manual script. Untested behaviour is proposed, not done. |
| One term, one meaning. | `settlement` and `merchant` are the only names for those things — in code, in tests, in commit messages, and in the UI copy merchants read. |
| Boundaries before bodies. | The 5 surfaces in `04-contracts.md` are fixed while changing them is free; after sign-off, a change to one needs its own requirement. |
| The domain stays pure. | Rules import no framework, no PostgreSQL, and no vendor SDK. Modular monolith with enforced boundaries only holds if this is checked, not intended. |
| Boring technology, justified additions. | 31 practices were selected for Fintech Payout Go; anything not among them needs an ADR naming what it replaces and what breaks without it. |
| Fail closed. | Deny by default. A settlement read without a resolved tenant is a failure, not an empty list. |
| Make it observable. | A failed settlement operation is a log line with a correlation id and the merchant it belonged to — including the ones you think cannot happen. |
| Reversible beats predictable. | Schema changes go forward only, behind a PostgreSQL migration; 12-week scope means something gets cut, so cut features, not rollback paths. |
| Stop and ask before guessing. | Three failed attempts on REQ-001 means the model of the problem is wrong. Escalate with what you tried and what you ruled out. |

## 2. Laws this profile adds

These bind because of what the product does, not because they are generally good.

| Law | Obligation |
| --- | --- |
| Money is never approximate. | A settlement that moves money writes a ledger entry in the same transaction as the state change. No balance is ever recomputed from events at read time. |
| Tenancy is not a parameter. | The tenant comes from the session. Any handler that reads it from a body or a query string is a bug, including in tests. |
| Personal data has a reason and a lifetime. | Every field has a stated purpose and retention; nothing personal lands in logs, fixtures or error details. |

## 3. Definition of done

A settlement change is done when all of the following are true for Fintech Payout Go. Not "mostly true".

- [ ] **G0-RUN** — The project starts from a clean clone with one documented command. _Here: for Fintech Payout Go: one command, and a missing variable is named._
- [ ] **G0-CHECK** — Lint or typecheck runs in CI on every pull request.
- [ ] **G0-SMOKE** — One happy-path smoke test exercises the primary user journey. _Here: one settlement taken from creation to done through the documented interface._
- [ ] **G1-CI** — The full test suite runs in CI on every pull request and is required to merge.
- [ ] 26 of 28 requirements carry an `@req` anchor; REQ-001 is the first, at `core_runnable_test.go`.
- [ ] A refund or reversal path exists and is tested for the settlement it applies to.
- [ ] At least one test proves a cross-tenant read is impossible.
- [ ] The change is reviewable in one sitting; if it is not, it is two changes.

## 4. Change protocol

| Change | What must happen first |
| --- | --- |
| New behaviour on a settlement | Add or amend a requirement in `spec.json`, then write the failing settlement test. |
| Changed settlement shape or error | Update the contract inventory in 04-contracts.md, then the test that pins it. |
| New dependency or service | ADR in 03-architecture.md: what it replaces, what breaks without it, and what removing it later would cost. |
| Test deletion or weakening | Not allowed as a fix for a settlement. Skip it with the requirement id and escalate instead. |
| Scope expansion | Edit the brief and remove something of comparable size in the same change. |
