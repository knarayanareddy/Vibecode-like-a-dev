# Delivery plan

> Generated by vibecode-like-a-dev v0.21.0 · kind agent · stage production · tier 3 (critical)

## 1. The shape of the work

Build the smallest end-to-end slice of **The primary journey works end to end** first: one screen or command, one operation, one storage path, one test per criterion, deployed. Then widen.

- A phase gate is a real gate. Do not start the next phase with a red check.
- Every task maps to a requirement id or a gate id. A task that maps to neither is a hobby.
- Calendar budget is 10 weeks; if the plan does not fit, cut scope in the brief — never cut gates.

## 2. Phases

### Phase 0 — Skeleton and guardrails · week 1-2

_A running, tested, documented box that can create and delete a disposition and nothing else._

- [ ] Initialise the repository with Python 3.12 and PostgreSQL; commit the lockfile.
- [ ] Add the CI workflow with lint, typecheck and test jobs, and make it required on the default branch.
- [ ] Add configuration validation that names every missing variable before the first disposition is created.
- [ ] Write the runbook: install, run, test, deploy, and what patients see when the disposition service is down.
- [ ] Copy the specification packet into the repository and wire the spec check into CI.
- [ ] Answer the open questions that block the disposition slice; the rest can wait for their phase.

**Exit:** The documented command creates and deletes a disposition through PostgreSQL, and CI is green on that alone.

### Phase 1 — Domain core · week 3-4

_The rules that make a disposition valid, in code, before any framework is chosen for them._

- [ ] Fill the language table around a disposition: one term, one meaning, no synonyms.
- [ ] Write failing tests for each rule a disposition must satisfy, including the ones the idea states in its own words.
- [ ] Implement the disposition aggregates as pure code with no framework, network or database imports.
- [ ] Define typed errors for the ways a disposition can be rejected; no exception control flow across module boundaries.
- [ ] Run the mutation check on the disposition domain and record the baseline score.

**Exit:** A disposition rules pass their tests with no infrastructure imported — no PostgreSQL, no framework.

### Phase 2 — Contracts before implementation · week 5-6

_Every boundary around a disposition fixed while changing it is still free._

- [ ] Fix each shape in the contract inventory: internal module interfaces behind the disposition use case.
- [ ] Write the acceptance tests for a disposition first; they must fail for missing behaviour, not missing setup.
- [ ] Record a real response for every external dependency, or write down the stub and why.
- [ ] Record an ADR for each library that a reviewer could plausibly want removed.

**Exit:** The disposition acceptance tests exist and fail because the behaviour is missing, not because the setup is.

### Phase 3 — Vertical slices · week 7-9

_Working disposition behaviour end to end, one requirement at a time._

- [ ] REQ-004 What Clinical Triage Python knows about a disposition survives a restart in PostgreSQL, and every schema change is a forward-only migration with a restore step that has been run once. Test first, then implement, then trace.
- [ ] REQ-005 A patient's disposition data has a stated retention period, an export, and a deletion path that removes every copy including the ones in logs and fixtures. Test first, then implement, then trace.
- [ ] REQ-018 A disposition record that contains PHI is unreadable without the key, on every path it travels, including backups and the export path. Test first, then implement, then trace.
- [ ] REQ-024 Each field a patient supplies is held for a named purpose with a named legal basis, not for "the product" in general. Test first, then implement, then trace.
- [ ] REQ-025 One request produces one complete file, and the patient can tell which request produced it. Test first, then implement, then trace.
- [ ] REQ-026 After erasure a search for the subject returns nothing except the non-personal audit of the erasure itself. Test first, then implement, then trace.
- [ ] REQ-027 The register is a build artifact with a test, not a document someone remembers to update. Test first, then implement, then trace.
- [ ] REQ-006 A patient signs in and signs out, and a revoked session stops working on the server immediately rather than at the next token expiry. Test first, then implement, then trace.
- [ ] REQ-007 Reading or changing another patient's disposition is refused by the server; the interface is allowed to hide the control but never to be the control. Test first, then implement, then trace.
- [ ] REQ-008 Two tenants cannot see or affect each other's disposition data through any query, handler or export path, and a patient who belongs to one tenant cannot reach another's rows. Test first, then implement, then trace.
- [ ] REQ-011 No irreversible effect on a disposition or an external service happens on model authority alone: a named privilegedActor approves the exact payload digest. Test first, then implement, then trace.
- [ ] REQ-014 Public entry points that create or change disposition data are limited per identity and per address, and say how long to wait when they refuse. Test first, then implement, then trace.
- [ ] REQ-015 Privileged changes to a disposition are append-only and attributable to a privileged user who made them, including the ones made by a support tool, and never to the patient whose data changed. Test first, then implement, then trace.
- [ ] REQ-019 A role that needs a name and an appointment time cannot read a diagnosis through the same endpoint, even though the database holds both. Test first, then implement, then trace.
- [ ] REQ-020 The product can be used in an emergency without weakening the default path: the exception is logged, time-boxed and visible. Test first, then implement, then trace.
- [ ] REQ-009 Model calls that touch disposition content have a timeout, a validated response, a cost ceiling, and a recorded fixture the evaluation runs against. Test first, then implement, then trace.
- [ ] REQ-010 The agent acting on a disposition can invoke only registered tools with schema-valid arguments, and prompt injection inside untrusted data cannot unlock unapproved actions. Test first, then implement, then trace.
- [ ] REQ-028 No person mistakes an automated output or recommendation for a human decision, and downstream systems can detect synthetic content programmatically. Test first, then implement, then trace.
- [ ] REQ-029 Human oversight is operational, not decorative: reviewers see confidence limits and inputs, can override any recommendation, and can disable automated recommendations via a stop control. Test first, then implement, then trace.
- [ ] REQ-C01 When the triage model classifies an intake as urgent, the service shall require explicit clinician confirmation before releasing the disposition. Test first, then implement, then trace.
- [ ] REQ-012 A runaway loop around a disposition terminates deterministically at its declared ceiling or within one step of a kill-switch signal, releasing held leases cleanly. Test first, then implement, then trace.
- [ ] REQ-013 A failed disposition operation is visible in a log with a correlation id the support team can search, without attaching a debugger to production. Test first, then implement, then trace.
- [ ] REQ-021 An audit entry written today is still readable, and still attributable, six years from now. Test first, then implement, then trace.
- [ ] REQ-023 A person discovering a suspected breach has a document that tells them who to call next and by when, and someone has already walked through it. Test first, then implement, then trace.

**Exit:** Each of the 31 requirements is traceable from criterion to test, with its anchor green in CI.

### Phase 4 — Interface and hardening · week 10-10

_Clinical Triage Python feels finished to a patient and fails predictably._

- [ ] Walk the threat model; each accepted mitigation becomes a control or a test.
- [ ] Add correlation IDs and one alert on error rate.
- [ ] Exercise every failure path in the requirements, manually or by test.
- [ ] Raise the mutation score to target on the domain layer.

**Exit:** All 27 gates pass in CI, and the manual checks have been run once and dated.

### Phase 5 — Release and first observation · week 11-10

_Ship a disposition change with a way back._

- [ ] Write the release checklist and the rollback procedure for a PostgreSQL migration.
- [ ] Deploy to staging and take one disposition through the primary journey there.
- [ ] Observe for one window: error rate, latency, and one disposition created by a real patient.
- [ ] Record what changed in the spec as a result, then archive the changed requirements.

**Exit:** A release has been observed with real patients data, and the rollback has been rehearsed or explicitly accepted as untested.

## 3. Commit and branch protocol

- One commit, one intention, prefixed with the requirement: `feat(REQ-001): runnable from a clean clone`.
- A commit that only adds tests is welcome; a commit that only weakens tests is rejected.
- Run ruff check . && mypy . && pytest before pushing — Python 3.12 will not tell you in CI either.
- One branch per vertical slice, and never two people inside the same disposition requirement.

## 4. Stop rules

Rules for humans and agents alike. The point is to stop the loop where the model of the problem is wrong, instead of paying for the same mistake repeatedly.

1. Three failed attempts at the same failing check: stop, write down what was tried, escalate with the evidence.
2. A test needs weakening to proceed: stop — that is either a wrong test or a wrong design.
3. A requirement about the disposition turns out to be ambiguous: stop that requirement, record the question, keep going elsewhere.
4. The phase gate cannot pass within twice its allotted time: cut scope; do not extend the phase silently.

## 5. Risk register

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| Scope creep past the 31 listed requirements | high | The non-goals table is the answer: anything unlisted is rejected in review rather than debated. |
| An invented abstraction around the disposition | medium | One context per owned noun; a new layer needs a reason a reviewer can check. |
| Environment and configuration drift | medium | Configuration is validated at startup and fails by naming the missing variable. |
| The 10-week calendar slipping | medium | Cut scope in the brief, never a gate. |
| Model output treated as trusted | high | Every response is schema-validated and budgeted; a timeout degrades, it does not half-write. |
| A personal-data field escaping its retention rule | high | Field-level inventory plus a deletion test that asserts zero rows remain. |

v1 is finished when all 27 gates in `05-verification.md` pass, every manual check is dated, and `spec.json` describes what was actually built — including the decisions that changed on the way.
