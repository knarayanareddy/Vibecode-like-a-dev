# Architecture

> Generated by vibecode-like-a-dev v0.21.0 · kind agent · stage production · tier 3 (critical)

## 1. Style decision

**Hexagonal task runner.** Model calls, tools and storage are adapters. The decision logic must be testable with recorded inputs and no network.

- Rejected: microservices — a disposition write would need a distributed transaction, and there is no team boundary to gain.
- Rejected: serverless-per-endpoint — the disposition lifecycle crosses several calls, and cold starts would be paid by a patient.
- Rejected: framework-shaped folders — they would put the disposition rules next to the transport code that is supposed to be the thinnest layer.

## 2. Shape

```text
transport   http                    (thin: parses, validates, maps errors)
     │ calls interfaces it does not own
application disposition use cases · actor and policy · transaction boundary
     │ domain types and errors only
domain      core · assistance · identity & access                    (pure: no PostgreSQL + SQLAlchemy Core/Alembic (forward-only migrations), no framework)
     ▲ implemented by
adapters    PostgreSQL + SQLAlchemy Core/Alembic (forward-only migrations) · model client · http clients

Imports point downward only. Anything pointing back up is a bug in Clinical Triage Python, not a shortcut.
```

## 3. Modules and import rules

| Module | Responsibility | May import | Must not import |
| --- | --- | --- | --- |
| Core | the product's central aggregate (name it) | its own disposition rules only | web framework, database driver, vendor SDK |
| Assistance | ModelCall, PromptContract | Core, and shared kernel types | web framework, database driver, vendor SDK |
| Identity & Access | Account, Session, Policy, Membership | Core, and shared kernel types | web framework, database driver, vendor SDK |
| Infrastructure / adapters | PostgreSQL, http clients | every context's interfaces for Record | the disposition rules of any context |

| Layer | Choice | Rationale |
| --- | --- | --- |
| language | Python 3.12 | Fewer moving parts means fewer invented abstractions. |
| runtime | CPython | Fewer moving parts means fewer invented abstractions. |

| validation | Pydantic at every boundary (input, env, external API) | Fewer moving parts means fewer invented abstractions. |
| tests | pytest for unit and integration, Playwright for the primary journey | Fast feedback for logic, one slow test for the journey. |

| logs | structlog with a correlation ID field | Fewer moving parts means fewer invented abstractions. |
| ci | GitHub Actions | Fewer moving parts means fewer invented abstractions. |

Declared constraints: FastAPI, SQLAlchemy. Keep them; record an ADR explaining how they fit, and do not add a second framework that duplicates their job.

## 5. Cross-cutting decisions

| Concern | Decision | Where it lives |
| --- | --- | --- |
| Configuration | Validated at startup against Pydantic at every boundary (input, env, external API); a missing value fails fast and is named | `config` module, one schema |
| Errors | Typed domain errors mapped to the envelope in `04-contracts.md`; internals never leak | `errors` module + transport mapper |
| Logging | Structured, with correlation and actor id on every line | `observability` module |
| Authorization | Checked in the application layer, deny by default, never in the client | `application` layer, one policy module |
| Time and IDs | Injected clock; opaque sortable ids | shared kernel |

## 6. The primary journey, in order

Written for **REQ-001 Runnable from a clean clone** — the first requirement, and the one whose shape the rest copy.

1. Transport receives the request and validates it against a schema.
2. The actor is resolved from the session; a request without one stops here.
3. The application layer loads the disposition, checks policy, and calls one domain operation.
4. The domain operation enforces the invariants in `02-domain-model.md` and returns a result or a typed error.
5. The adapter writes to PostgreSQL in one transaction and emits any domain event after commit.
6. Transport maps the result to the contract shape in `04-contracts.md`, including the correlation id.

## 7. Decision records

Non-functional targets for Clinical Triage Python go here too: latency on the disposition write path, availability, recovery time. A number with no measurement method is a slogan, so write "not measured in v1" instead of pretending.

**ADR-001 — Architecture: Hexagonal task runner**
Model calls, tools and storage are adapters. The decision logic must be testable with recorded inputs and no network. _Consequence:_ Boundaries are checked by an import rule in CI, not by review.

**ADR-002 — Persistence: PostgreSQL + SQLAlchemy Core/Alembic (forward-only migrations)**
Invariants that must hold across rows belong in the database, not only in code. _Consequence:_ Migration for every schema change is forward-only with a restore step.

**ADR-003 — Authorization: policy checked server-side, deny by default**
Client-side checks are hints, not controls; the server is the only caller that cannot be edited. _Consequence:_ Every read and write takes an actor, and the policy test is written before the handler.

**ADR-005 — Tenancy: tenant key resolved server-side and applied in the data layer**
A tenant filter applied at call sites is forgotten exactly once, and that once is an incident. _Consequence:_ Every query goes through the scoped repository; a forged tenant id is rejected before any read.

**ADR-009 — Model calls: contract in, validated out, budgeted**
A model call is an untrusted dependency that can be slow, wrong and expensive at once. _Consequence:_ Every call has a timeout, a schema check on the response, and a per-task cost cap.

Add an ADR for every dependency around a disposition that would take more than a day to remove, and for every boundary decision a future reader would otherwise reverse-engineer from this repository.

## 8. Fitness functions

Architecture that is not executable is decoration, so each of these runs in CI for Clinical Triage Python rather than living in a review checklist.

| Property | Check | Automated how | Fails when |
| --- | --- | --- | --- |
| Domain purity | No framework, database driver or vendor SDK imported under `domain/` | import-boundary rule in CI | A domain file imports infrastructure |
| Module boundaries | The 3 contexts import only their own domain and the shared kernel | import-boundary rule | A cross-context import appears |
| Contract agreement | Implementation matches the shapes in 04-contracts.md | contract test | A response field is added or removed silently |
| Requirement coverage | 29 anchored requirements have a passing test | `node ./spec-check.mjs` | A test is deleted or renamed |
| Test quality | Mutation score on the domain layer | mutation run in CI | A test would pass if the behaviour were wrong |

## 9. When this architecture should change

- A single disposition operation needs to scale on a different curve from the rest, measured rather than predicted.
- A disposition write starts spanning more than two of the 3 contexts and cannot be made eventually consistent without rewriting the rules.
- The tests for disposition rules need PostgreSQL running to pass: that is a broken boundary, not a reason to add a service.
