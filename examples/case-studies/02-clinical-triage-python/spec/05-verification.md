## 2. Anchors: how a requirement stays bound to a test

Every automated requirement carries one anchor line in the test that proves it. The example below is REQ-001, so it is the one you will write first.

```python
# @req REQ-001  # @req-ignore: example inside a spec document
def test_runnable_from_a_clean_clone_ac_01():
    # Given a fresh clone and an empty environment file, when the documented setup command runs, then it either succeeds or lists every missing required var
    result = execute_under_test()
    assert result is not None
```

- An anchor inside `tests/` counts as proof; an anchor in the disposition handler does not.
- Two anchors on one requirement are fine and both are counted; zero on any of the 29 automated requirements is a failure.
- Renaming or deleting the test that proves REQ-001 fails the spec check — that is the point of the anchor.

## 5. Spec check in CI

The packet ships a dependency-free checker. Put it in CI before the first disposition handler exists, so the anchors are enforced from commit one.

```yaml
name: spec
on: [pull_request]
jobs:
  spec:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - name: Run packet drift guard and gates
        run: |
          PACKET_DIR="$(dirname "$(git ls-files '*/spec-check.mjs' 'spec-check.mjs' | head -n1)")"
          node "$PACKET_DIR/spec-check.mjs" --repo . --strict --require-assertions
          node "$PACKET_DIR/enforcement/gates.mjs" --repo . --strict
```

Run it locally from this packet folder with `node ./spec-check.mjs` (pass `--repo <root>` from elsewhere); add `--strict --require-assertions` in release CI so pending requirements and hollow tests cannot ship silently.

What it fails on: a missing document, one of the 29 automated requirements without an anchor, an anchor naming a requirement that does not exist, a requirement with no criteria, and a practice reference that has disappeared.

The gates in section 4 are also a command: `node ./enforcement/gates.mjs`, generated from this packet, 26 checks, no dependencies. It is deliberately blunt — it proves a runbook exists and names an owner, not that the owner knows the product — and every check prints what it cannot see. `enforcement/README.md` is the table.

## 6. Mutation testing

- Run mutmut (`mutmut run`, configured in `pyproject.toml`) on the domain layer only. Transport and adapter code produces noise, not signal.
- Start from the current score and ratchet: the CI threshold only moves up.
- An equivalent mutant is suppressed in configuration with a one-line comment explaining why it is equivalent.
- A surviving mutant in an invariant means the test asserts the wrong thing. Fix the test, not the mutant.

## 8. Review checklist

- [ ] The diff implements one of `spec.json`'s requirements and nothing beyond it.
- [ ] The failure path of the disposition change exists in code and in a test.
- [ ] No test was weakened, skipped or deleted to make CI pass.
- [ ] The traceability row is updated and its anchor is green.
- [ ] No personal field of a patient reaches a log, fixture or error detail.
- [ ] Every new read of another patient's disposition is authorized server-side.
- [ ] New dependency? ADR present, pinned, removable in a day.

Deliberately absent: a coverage percentage target (it rewards executing code, not checking it), mocks of the domain to test the domain, and tests of framework behaviour. Reasoning: `testing.test-budget` in the library.
