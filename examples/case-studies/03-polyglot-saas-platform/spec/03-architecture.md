# Architecture

> Generated by vibecode-like-a-dev v0.20.0 · kind web-app · stage production · tier 3 (critical)

## 1. Style decision

**Modular monolith with enforced boundaries.** One deployable, several modules, boundaries checked mechanically. Microservices multiply failure modes before a product has found its shape; the seams here are the ones that survive the split if it ever comes.

- Rejected: microservices — an analytics write would need a distributed transaction, and there is no team boundary to gain.
- Rejected: serverless-per-endpoint — the analytics lifecycle crosses several calls, and cold starts would be paid by a tenant.
- Rejected: framework-shaped folders — they would put the analytics rules next to the transport code that is supposed to be the thinnest layer.

## 2. Shape

```text
transport   http                    (thin: parses, validates, maps errors)
     │ calls interfaces it does not own
application analytics use cases · actor and policy · transaction boundary
     │ domain types and errors only
domain      core · identity & access · jobs · integrations                    (pure: no PostgreSQL + pgx, forward-only migrations with goose, no framework)
     ▲ implemented by
adapters    PostgreSQL + pgx, forward-only migrations with goose · queue · http clients

Imports point downward only. Anything pointing back up is a bug in Polyglot Saas Platform, not a shortcut.
```

## 3. Modules and import rules

| Module | Responsibility | May import | Must not import |
| --- | --- | --- | --- |
| Core | the product's central aggregate (name it) | its own analytics rules only | web framework, database driver, vendor SDK |
| Identity & Access | Account, Session, Policy, Membership | Core, and shared kernel types | web framework, database driver, vendor SDK |
| Jobs | Job, Attempt | Core, and shared kernel types | web framework, database driver, vendor SDK |
| Integrations | Endpoint, Delivery, IdempotencyKey | Core, and shared kernel types | web framework, database driver, vendor SDK |
| Infrastructure / adapters | PostgreSQL, http clients, queue | every context's interfaces for Record | the analytics rules of any context |

## 4. Stack

| Layer | Choice | Rationale |
| --- | --- | --- |
| language | web: TypeScript (strict) · api: Go 1.23 · worker: Rust (2021 edition) | Fewer moving parts means fewer invented abstractions. |
| runtime | the Go toolchain, shipped as a single static binary | Fewer moving parts means fewer invented abstractions. |
| ui | web: React + Vite (only if a UI is in scope) | Fewer moving parts means fewer invented abstractions. |
| http | net/http with chi, typed handlers and explicit error returns | Fewer moving parts means fewer invented abstractions. |
| db | PostgreSQL + pgx, forward-only migrations with goose | Boring and relational beats novel and eventual for a first version. |
| validation | explicit decode and validation at the boundary (no reflection magic) | Fewer moving parts means fewer invented abstractions. |
| tests | web: Vitest; api: go test; worker: cargo test | Fast feedback for logic, one slow test for the journey. |
| lint | web: npm run lint; api: golangci-lint run; worker: cargo clippy --all-targets -- -D warnings | Fewer moving parts means fewer invented abstractions. |
| logs | slog with a correlation ID field | Fewer moving parts means fewer invented abstractions. |
| ci | GitHub Actions | Fewer moving parts means fewer invented abstractions. |

This is the default. Override it only through an ADR that names the trade-off; the tests and gates do not depend on any specific framework.

## 5. Cross-cutting decisions

| Concern | Decision | Where it lives |
| --- | --- | --- |
| Configuration | Validated at startup against explicit decode and validation at the boundary (no reflection magic); a missing value fails fast and is named | `config` module, one schema |
| Errors | Typed domain errors mapped to the envelope in `04-contracts.md`; internals never leak | `errors` module + transport mapper |
| Logging | Structured, with correlation and actor id on every line | `observability` module |
| Authorization | Checked in the application layer, deny by default, never in the client | `application` layer, one policy module |
| Time and IDs | Injected clock; opaque sortable ids | shared kernel |
| Feature flags | One mechanism, default off for new behaviour | `config` module |

## 6. The primary journey, in order

Written for **REQ-001 Runnable from a clean clone** — the first requirement, and the one whose shape the rest copy.

1. Transport receives the request and validates it against a schema.
2. The actor is resolved from the session; a request without one stops here.
3. The application layer loads the tenant, checks policy, and calls one domain operation.
4. The domain operation enforces the invariants in `02-domain-model.md` and returns a result or a typed error.
5. The adapter writes to PostgreSQL in one transaction and emits any domain event after commit.
6. Transport maps the result to the contract shape in `04-contracts.md`, including the correlation id.

## 7. Decision records

Non-functional targets for Polyglot Saas Platform go here too: latency on the analytics write path, availability, recovery time. A number with no measurement method is a slogan, so write "not measured in v1" instead of pretending.

**ADR-001 — Architecture: Modular monolith with enforced boundaries**
One deployable, several modules, boundaries checked mechanically. Microservices multiply failure modes before a product has found its shape; the seams here are the ones that survive the split if it ever comes. _Consequence:_ Boundaries are checked by an import rule in CI, not by review.

**ADR-002 — Persistence: PostgreSQL + pgx, forward-only migrations with goose**
Invariants that must hold across rows belong in the database, not only in code. _Consequence:_ Migration for every schema change is forward-only with a restore step.

**ADR-003 — Authorization: policy checked server-side, deny by default**
Client-side checks are hints, not controls; the server is the only caller that cannot be edited. _Consequence:_ Every read and write takes an actor, and the policy test is written before the handler.

**ADR-005 — Tenancy: tenant key resolved server-side and applied in the data layer**
A tenant filter applied at call sites is forgotten exactly once, and that once is an incident. _Consequence:_ Every query goes through the scoped repository; a forged tenant id is rejected before any read.

Add an ADR for every dependency around an analytics that would take more than a day to remove, and for every boundary decision a future reader would otherwise reverse-engineer from this repository.

## 8. Fitness functions

Architecture that is not executable is decoration, so each of these runs in CI for Polyglot Saas Platform rather than living in a review checklist.

| Property | Check | Automated how | Fails when |
| --- | --- | --- | --- |
| Domain purity | No framework, database driver or vendor SDK imported under `domain/` | import-boundary rule in CI | A domain file imports infrastructure |
| Module boundaries | The 4 contexts import only their own domain and the shared kernel | import-boundary rule | A cross-context import appears |
| Token usage | No raw colour or spacing literal in a component | token lint | A hex colour appears in a component |
| Contract agreement | Implementation matches the shapes in 04-contracts.md | contract test | A response field is added or removed silently |
| Requirement coverage | 21 anchored requirements have a passing test | `node ./spec-check.mjs` | A test is deleted or renamed |
| Test quality | Mutation score on the domain layer | mutation run in CI | A test would pass if the behaviour were wrong |

## 9. When this architecture should change

- A single analytics operation needs to scale on a different curve from the rest, measured rather than predicted.
- An analytics write starts spanning more than two of the 4 contexts and cannot be made eventually consistent without rewriting the rules.
- The tests for analytics rules need PostgreSQL running to pass: that is a broken boundary, not a reason to add a service.
