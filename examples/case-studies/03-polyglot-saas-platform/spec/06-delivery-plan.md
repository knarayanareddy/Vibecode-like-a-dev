# Delivery plan

> Generated by vibecode-like-a-dev v0.21.0 · kind web-app · stage production · tier 3 (critical)

## 1. The shape of the work

Build the smallest end-to-end slice of **The primary journey works end to end** first: one screen or command, one operation, one storage path, one test per criterion, deployed. Then widen.

- A phase gate is a real gate. Do not start the next phase with a red check.
- Every task maps to a requirement id or a gate id. A task that maps to neither is a hobby.
- Calendar budget is 10 weeks; if the plan does not fit, cut scope in the brief — never cut gates.

## 2. Phases

### Phase 0 — Skeleton and guardrails · week 1-2

_A running, tested, documented box that can create and delete an analytics and nothing else._

- [ ] Initialise the repository with web: TypeScript (strict) · api: Go 1.23 · worker: Rust (2021 edition) and PostgreSQL; commit the lockfile.
- [ ] Add the CI workflow with lint, typecheck and test jobs, and make it required on the default branch.
- [ ] Add configuration validation that names every missing variable before the first analytics is created.
- [ ] Write the runbook: install, run, test, deploy, and what tenants see when the analytics service is down.
- [ ] Copy the specification packet into the repository and wire the spec check into CI.
- [ ] Answer the open questions that block the analytics slice; the rest can wait for their phase.

**Exit:** The documented command creates and deletes an analytics through PostgreSQL, and CI is green on that alone.

### Phase 1 — Domain core · week 3-4

_The rules that make an analytics valid, in code, before any framework is chosen for them._

- [ ] Fill the language table around an analytics: one term, one meaning, no synonyms.
- [ ] Write failing tests for each rule an analytics must satisfy, including the ones the idea states in its own words.
- [ ] Implement the analytics aggregates as pure code with no framework, network or database imports.
- [ ] Define typed errors for the ways an analytics can be rejected; no exception control flow across module boundaries.
- [ ] Run the mutation check on the analytics domain and record the baseline score.

**Exit:** An analytics rules pass their tests with no infrastructure imported — no PostgreSQL, no framework.

### Phase 2 — Contracts before implementation · week 5-6

_Every boundary around an analytics fixed while changing it is still free._

- [ ] Fix each shape in the contract inventory: REQ-013, REQ-014.
- [ ] Write the acceptance tests for an analytics first; they must fail for missing behaviour, not missing setup.
- [ ] Record a real response for every external dependency, or write down the stub and why.
- [ ] Record an ADR for each library that a reviewer could plausibly want removed.

**Exit:** The analytics acceptance tests exist and fail because the behaviour is missing, not because the setup is.

### Phase 3 — Vertical slices · week 7-9

_Working analytics behaviour end to end, one requirement at a time._

- [ ] REQ-004 What Polyglot Saas Platform knows about an analytics survives a restart in PostgreSQL, and every schema change is a forward-only migration with a restore step that has been run once. Test first, then implement, then trace.
- [ ] REQ-005 A tenant's analytics data has a stated retention period, an export, and a deletion path that removes every copy including the ones in logs and fixtures. Test first, then implement, then trace.
- [ ] REQ-021 Each field a tenant supplies is held for a named purpose with a named legal basis, not for "the product" in general. Test first, then implement, then trace.
- [ ] REQ-022 One request produces one complete file, and the tenant can tell which request produced it. Test first, then implement, then trace.
- [ ] REQ-023 After erasure a search for the subject returns nothing except the non-personal audit of the erasure itself. Test first, then implement, then trace.
- [ ] REQ-024 The register is a build artifact with a test, not a document someone remembers to update. Test first, then implement, then trace.
- [ ] REQ-006 A tenant signs in and signs out, and a revoked session stops working on the server immediately rather than at the next token expiry. Test first, then implement, then trace.
- [ ] REQ-007 Reading or changing another tenant's analytics is refused by the server; the interface is allowed to hide the control but never to be the control. Test first, then implement, then trace.
- [ ] REQ-008 Two tenants cannot see or affect each other's analytics data through any query, handler or export path, and a tenant who belongs to one tenant cannot reach another's rows. Test first, then implement, then trace.
- [ ] REQ-017 Public entry points that create or change analytics data are limited per identity and per address, and say how long to wait when they refuse. Test first, then implement, then trace.
- [ ] REQ-018 Privileged changes to an analytics are append-only and attributable to a privileged user who made them, including the ones made by a support tool, and never to the tenant whose data changed. Test first, then implement, then trace.
- [ ] REQ-C01 When a tenant exceeds 10 scheduled exports per hour, the worker shall defer new jobs with QUOTA_EXCEEDED. Test first, then implement, then trace.
- [ ] REQ-013 The analytics interface has a versioned, machine-readable contract kept in the repository, and a breaking change fails before merge rather than after a consumer notices. Test first, then implement, then trace.
- [ ] REQ-014 Every failure on the analytics interface returns one envelope shape, with an opaque identifier a support conversation can quote. Test first, then implement, then trace.
- [ ] REQ-015 A retried analytics request produces the same outcome as the first one: no second record, no second side effect, no second notification. Test first, then implement, then trace.
- [ ] REQ-016 A failed analytics operation is visible in a log with a correlation id the support team can search, without attaching a debugger to production. Test first, then implement, then trace.

**Exit:** Each of the 25 requirements is traceable from criterion to test, with its anchor green in CI.

### Phase 4 — Interface and hardening · week 10-10

_Polyglot Saas Platform feels finished to a tenant and fails predictably._

- [ ] REQ-009 The main analytics journey completes with a keyboard and a screen reader, error states included, and focus lands somewhere sensible after every navigation.
- [ ] REQ-010 Every analytics screen has loading, empty, error and success states, and the error state carries the next action rather than an apology.
- [ ] REQ-011 Colour, spacing and type come from one token source, so restyling the analytics views is a change to one file and not to every component.
- [ ] REQ-012 An analytics failure is classified before it is rendered, so the message tells the tenant what to do next and never leaks an identifier they cannot act on.
- [ ] Bind every component to design tokens; remove raw values.
- [ ] Walk the threat model; each accepted mitigation becomes a control or a test.
- [ ] Add correlation IDs and one alert on error rate.
- [ ] Exercise every failure path in the requirements, manually or by test.
- [ ] Raise the mutation score to target on the domain layer.

**Exit:** All 23 gates pass in CI, and the manual checks have been run once and dated.

### Phase 5 — Release and first observation · week 11-10

_Ship an analytics change with a way back._

- [ ] Write the release checklist and the rollback procedure for a PostgreSQL migration.
- [ ] Deploy to staging and take one analytics through the primary journey there.
- [ ] Observe for one window: error rate, latency, and one analytics created by a real tenant.
- [ ] Record what changed in the spec as a result, then archive the changed requirements.

**Exit:** A release has been observed with real tenants data, and the rollback has been rehearsed or explicitly accepted as untested.

## 3. Commit and branch protocol

- One commit, one intention, prefixed with the requirement: `feat(REQ-001): runnable from a clean clone`.
- A commit that only adds tests is welcome; a commit that only weakens tests is rejected.
- Run (cd web && npm run lint && npm run typecheck && npm test) && (cd api && golangci-lint run && go vet ./... && go test ./...) && (cd worker && cargo clippy --all-targets -- -D warnings && cargo check --all-targets && cargo test) before pushing — web: TypeScript (strict) · api: Go 1.23 · worker: Rust (2021 edition) will not tell you in CI either.
- One branch per vertical slice, and never two people inside the same analytics requirement.

## 4. Stop rules

Rules for humans and agents alike. The point is to stop the loop where the model of the problem is wrong, instead of paying for the same mistake repeatedly.

1. Three failed attempts at the same failing check: stop, write down what was tried, escalate with the evidence.
2. A test needs weakening to proceed: stop — that is either a wrong test or a wrong design.
3. A requirement about the analytics turns out to be ambiguous: stop that requirement, record the question, keep going elsewhere.
4. The phase gate cannot pass within twice its allotted time: cut scope; do not extend the phase silently.

## 5. Risk register

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| Scope creep past the 25 listed requirements | high | The non-goals table is the answer: anything unlisted is rejected in review rather than debated. |
| An invented abstraction around the analytics | medium | One context per owned noun; a new layer needs a reason a reviewer can check. |
| Environment and configuration drift | medium | Configuration is validated at startup and fails by naming the missing variable. |
| The 10-week calendar slipping | medium | Cut scope in the brief, never a gate. |
| A personal-data field escaping its retention rule | high | Field-level inventory plus a deletion test that asserts zero rows remain. |

v1 is finished when all 23 gates in `05-verification.md` pass, every manual check is dated, and `spec.json` describes what was actually built — including the decisions that changed on the way.
