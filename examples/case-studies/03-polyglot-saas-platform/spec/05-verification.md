# Verification

> Generated by vibecode-like-a-dev v0.20.0 · kind web-app · stage production · tier 3 (critical)

> Coverage measures execution; assertions measure whether a test would notice an analytics going wrong. This plan optimises for the second and binds 21 of 25 requirements to a named test, so Polyglot Saas Platform cannot drift away from its spec without CI saying so.

## 1. Test layers

| Layer | What it proves | Tool | Volume |
| --- | --- | --- | --- |
| Domain unit | Invariants and state transitions, with no IO | web: Vitest · api: go test · worker: cargo test | most tests live here |
| Application | Use case orchestration, authorization, transaction boundaries | same runner, fake adapters | a few per use case |
| Contract | Interface shapes and error envelopes | contract tests + fixtures | one per endpoint |
| Acceptance | The requirement criteria, end to end through the public surface | integration harness | one per criterion |
| Journey | The primary user path in a real browser | Playwright | one, maybe two |
| Property | Invariants across generated inputs | rapid | per core invariant |

## 2. Anchors: how a requirement stays bound to a test

Every automated requirement carries one anchor line in the test that proves it. The example below is REQ-001, so it is the one you will write first.

```go
// @req REQ-001  // @req-ignore: example inside a spec document
func TestRunnableFromACleanCloneAc01(t *testing.T) {
	// Given a fresh clone and an empty environment file, when the documented setup command runs, then it either succeeds or lists every missing required var
	if err := executeUnderTest(); err != nil {
		t.Fatalf("unexpected error: %v", err)
	}
}
```

- An anchor inside `api/` counts as proof; an anchor in the analytics handler does not.
- Two anchors on one requirement are fine and both are counted; zero on any of the 21 automated requirements is a failure.
- Renaming or deleting the test that proves REQ-001 fails the spec check — that is the point of the anchor.

## 4. Gates for tier 3

- [ ] **G0-CHECK** — Lint or typecheck runs in CI on every pull request.

- [ ] **G1-CI** — The full test suite runs in CI on every pull request and is required to merge.
- [ ] **G1-DOMAIN-TESTS** — Every rule in the domain model has at least one automated test. _Here: 5 core requirements, each with a test on the tenant rules._
- [ ] **G1-AC-TRACE** — Every requirement marked automated maps to a named test through an @req anchor. _Here: 21 automated requirements, 3 manual — anchor in the test file, not the doc._

## 5. Spec check in CI

The packet ships a dependency-free checker. Put it in CI before the first analytics handler exists, so the anchors are enforced from commit one.

```yaml
name: spec
on: [pull_request]
jobs:
  spec:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - name: Run packet drift guard and gates
        run: |
          PACKET_DIR="$(dirname "$(git ls-files '*/spec-check.mjs' 'spec-check.mjs' | head -n1)")"
          node "$PACKET_DIR/spec-check.mjs" --repo . --strict --require-assertions
          node "$PACKET_DIR/enforcement/gates.mjs" --repo . --strict
```

Run it locally from this packet folder with `node ./spec-check.mjs` (pass `--repo <root>` from elsewhere); add `--strict --require-assertions` in release CI so pending requirements and hollow tests cannot ship silently.

What it fails on: a missing document, one of the 21 automated requirements without an anchor, an anchor naming a requirement that does not exist, a requirement with no criteria, and a practice reference that has disappeared.

The gates in section 4 are also a command: `node ./enforcement/gates.mjs`, generated from this packet, 22 checks, no dependencies. It is deliberately blunt — it proves a runbook exists and names an owner, not that the owner knows the product — and every check prints what it cannot see. `enforcement/README.md` is the table.

## 6. Mutation testing

- Run go-mutesting (`go-mutesting ./...`, configured in `.go-mutesting.json`) on the domain layer only. Transport and adapter code produces noise, not signal.
- Start from the current score and ratchet: the CI threshold only moves up.
- An equivalent mutant is suppressed in configuration with a one-line comment explaining why it is equivalent.
- A surviving mutant in an invariant means the test asserts the wrong thing. Fix the test, not the mutant.

## 7. Manual checks

3 requirement(s) are verified manually: REQ-003, REQ-009, REQ-010. Run each of their criteria in `spec.json` once and record the date and the observer. An unrun manual check is a claim, not evidence.

## 8. Review checklist

- [ ] The diff implements one of `spec.json`'s requirements and nothing beyond it.
- [ ] The failure path of the analytics change exists in code and in a test.
- [ ] No test was weakened, skipped or deleted to make CI pass.
- [ ] The traceability row is updated and its anchor is green.
- [ ] No personal field of a tenant reaches a log, fixture or error detail.
- [ ] Every new read of another tenant's analytics is authorized server-side.
- [ ] New dependency? ADR present, pinned, removable in a day.

Deliberately absent: a coverage percentage target (it rewards executing code, not checking it), mocks of the domain to test the domain, and tests of framework behaviour. Reasoning: `testing.test-budget` in the library.
