# v0.19.0 VLD audit — confirmation review

**Reviewed:** 2026-11-02
**Method:** source review of the named Core, Runtime, compiler, evaluator, CLI, Studio, CI, tests, and documentation paths on the v0.19.0 baseline; targeted local searches and tests where useful. This is a confirmation review, not a penetration test and not evidence that an exploit was executed against a hosted service.

## Result

The supplied audit is substantially accurate. **Fifteen findings are confirmed as stated or with only minor wording qualifications; two are confirmed but are narrower than their title implies; one documentation finding is mixed because a count was accurate before the new Phase 1 practice was added.** The most important remediation order is: protect evaluator/live-run boundaries (3), make Runtime’s external-authority boundary explicit or provider-backed (1), fix ordered overlay composition and archival atomicity (2), then address CLI/auth/parser, source scanning, and output-path correctness.

| # | Finding | Review result | Evidence / qualification |
| --- | --- | --- | --- |
| 1 | Runtime receipts are not external GitHub/CI proof | **Confirmed** | `runtimeForgeEvidence()` checks a locally chained ledger and matching candidate/verification/approval/queue SHA/policy tuple. It does not query a forge, resolve a remote ref, validate a PR, or verify CI/protection status. This is a trust-boundary issue if consumers describe the receipt as external delivery truth. |
| 2 | Overlay/change history ordering and persistence defects | **Confirmed** | Planner target checks run against the base catalog before ordered overlays are applied. `archiveChange()` writes overlay/profile state before recompile/validation completes; provenance records additions even if a later overlay removes them; and history’s prior-ID calculation uses only the current requirement set. |
| 3 | Evaluator/live-agent execution can cross the harness trust boundary | **Confirmed** | `runExternalAgent()` permits in-workspace writes, `runNodeScript()` inherits its environment, and an evaluated workspace module can be imported in-process. A malicious or compromised task/runner can alter oracle/harness material or access live-provider credentials. “Write only in workspace” is not isolation. |
| 4 | Adoption schema detector is broken | **Confirmed** | `detectSchemaSignals()` uses `.filter((file) => /model|entity|schema/i)`, returning every filename because the RegExp object is truthy. It should test the filename. |
| 5 | `spec-check` misses source-only anchors and EARS vagueness | **Confirmed** | The source-only condition combines `inTests.length > 0` with `hits.every(... !isTest)`, making the branch unreachable. The emitted guard does not call the EARS vague-language check, and its strict mode has no assertion-density equivalent. |
| 6 | Output writers can follow a dangling final symlink | **Confirmed, scoped** | Several final-file writers use `existsSync()` followed by direct write/copy and do not `lstat()` a dangling final target. That includes artifact/change/export-related paths. Ancestor protections and `emitPacket()`’s component walk reduce the scope; it is not correct to describe every packet output path as equally exposed. |
| 7 | GitHub merge preflight can accept stale/partial evidence | **Confirmed** | Reviews are not constrained to the planned head SHA, check-run pagination is not completed, and matching a successful check by name can accept an older run while a newer required run is failing. |
| 8 | Placeholder-secret allowance is overly broad | **Confirmed** | `SECRET_ALLOW` is applied to the whole source line and includes broad alternatives such as `<`, `...`, and `example`; realistic credential-bearing strings can therefore be permitted by unrelated prose on the same line. |
| 9 | Requirement anchors are same-line, single-match, and three-digit-only | **Confirmed** | Both verifier/gate guard patterns use `@req\s+(REQ-\d{3})` without a global scan. A preceding-line comment, a second ID, or `REQ-1000` does not behave as the documentation implies. |
| 10 | Emitter/MCP output drift and misleading generated guidance | **Confirmed** | Generated API conventions describe selected-practice behavior unconditionally; `get_requirements()` always emits a TypeScript anchor; language selection recognizes exact `Python`/`Go` and falls back to `ts`; and the aggregate hint looks for an obsolete ops identifier rather than the delivery primitive. |
| 11 | Runtime CLI cannot reliably use remote allocation | **Confirmed** | The parser treats `--id` as an option while `store init` expects it as a positional directory. `runtime allocate` does not offer an explicit remote endpoint/base URL path, and the server’s idempotency requirement conflicts with a missing lease token on a first allocation. |
| 12 | Runtime status events are truncated in UI responses | **Confirmed** | Runtime state keeps a bounded recent-events projection; the Studio-facing status response uses that projection. Historic receipt detail can disappear even though the JSONL ledger remains durable. |
| 13 | MCP JSON-RPC validation is incomplete | **Confirmed** | Non-object/array inputs do not consistently return JSON-RPC `-32600`, numeric controls are coerced/clamped rather than schema-rejected, and request body accumulation has no explicit maximum. |
| 14 | VS Code extension’s HTTP response body is unbounded | **Confirmed** | `runtimeStatus()` concatenates every response chunk before parsing. The extension does sanitize display values afterward, but it has no response-byte cap at transport time. |
| 15 | CI/package hardening remains incomplete | **Confirmed** | There is no committed Dependabot configuration; workflow/action drift and lack of shell-command timeouts remain maintainability/reliability concerns. Exact severity depends on the repository’s operational threat model. |
| 16 | High-value test gaps remain | **Confirmed** | Existing tests did not cover the audit’s critical ordered-overlay composition, stale GitHub status/approval, dangling-final-symlink, archive rollback, or hostile evaluator cases. |
| 17 | Authoring/README documentation drifts from implementation | **Mixed / confirmed in part** | The front-matter example shows nested YAML despite the project’s intentionally simple front-matter parser, and docs imply anchor behavior the scanners do not provide. The tier-0 table says 140 lines while policy allows 160. The README count of 34 was accurate immediately before this Phase 1 work; after the added practice it is now stale and must say 35. |
| 18 | Git/catalog error diagnostics can expose local paths or remote URLs | **Confirmed** | Raw `stderr`/exception text is interpolated into several error paths. These are useful developer diagnostics but should be structured/sanitized at untrusted or user-visible boundaries. |

## Recommended remediation sequence

### P0 — trust and execution boundary

- [ ] Make local Runtime receipts unambiguously local evidence in every public API/document, or add an explicitly optional provider attestation verifier that binds immutable remote ref/PR/check data.
- [ ] Run outcome tasks and external agents in an OS/container sandbox with a read-only harness/oracle mount, separate writable workspace, explicit network policy, and a scrubbed allowlist environment.
- [ ] Treat task fixtures, runners, and provider output as untrusted; validate them across a process boundary before importing or reporting them.

### P1 — correctness and authorization

- [ ] Apply overlays sequentially to the evolving catalog, then validate targets against the corresponding state; add dependency/order fixtures.
- [ ] Make change archive output transactional (stage, compile/validate, atomic promote) and retain retired IDs from prior history, not just the final manifest.
- [ ] Correct `detectSchemaSignals()` to `/.../.test(file)` and add representative/non-representative tests.
- [ ] Require GitHub reviews and checks for the exact planned head SHA, paginate all required endpoints, and use each check’s latest completed attempt/status rather than “any success by name.”
- [ ] Narrow secret placeholders to exact tokens/structured fixture sources rather than a line-wide regex allowance.
- [ ] Validate final destinations with `lstat()` before every destructive write/copy; reject links including dangling links and use an atomic sibling-file replace where possible.

### P2 — contract and developer experience

- [ ] Reconcile `verify` and emitted `spec-check`: global/multi-ID anchor extraction, four-or-more digit IDs, documented preceding-line association if intended, and matching EARS/assertion checks.
- [ ] Derive MCP anchors, document fences, primitive IDs, and language labels from one plan/model source; add snapshot/parity tests.
- [ ] Repair CLI option parsing and define a complete remote Runtime client contract, including first-allocation idempotency semantics.
- [ ] Return a paginated or explicitly complete event history; do not label a bounded recent projection as full receipt history.
- [ ] Validate JSON-RPC envelopes and parameter types before dispatch and cap request/response sizes in MCP, Studio, and extension transport.
- [ ] Add workflow command timeouts, dependency-update policy, and pinned-action upkeep checks appropriate to project maintenance.

### P3 — tests, docs, diagnostics

- [ ] Add regression tests for each P0/P1 behavior, including hostile task/runner and filesystem-link fixtures.
- [ ] Align AUTHORING/README examples with the actual parser/scanner, generate repository statistics where practical, and keep version/history text deduplicated.
- [ ] Convert raw subprocess/remote errors to typed error codes plus safe summaries; reserve full diagnostic output for an explicit local debug mode.

## Non-remediation decision in this phase

This review deliberately does not change the audited subsystems. The concurrent Phase 1 public-web discoverability work stays deterministic, dependency-free, opt-in, and without network/credential/crawler behavior. Remediation should be planned as separately scoped work because items 1–18 change trust, execution, or compatibility contracts.
